## 时序体系（核心设计）

- 栅格：全曲 0.1s/槽 = 2 游戏刻；`slot = round(绝对秒×10)`。
- 链：`[启动源][中继器×m(Σdelay)][红线+音符盒]…`，累积延迟 = Σ2×delay 刻，精确等于 0.1s×槽位。
- 音符触发：红线正上方音符盒（仅竖琴线，Up 供电）在第 σ 槽；左右"枝路"（1 中继器 delay=1 + 音符盒）挂在前一槽红线上，第 σ+1 槽发声——分毫不差。
- 间隙压缩：静默段用大延迟中继器（每 4 槽 1 格），所有轨道共用同一 slotToZ 映射，波前永不离散。
- 自检：`ChainCompiler.validate` 在每次编译后重放整条链，任何时刻失配立即抛异常（放置前失败）。

## 游戏内使用流程

1. 启动游戏，游戏根目录出现 `midi/` 文件夹，放入 `.mid` 文件。
2. 创造模式取出"音乐生成器"，Shift+右键打开浏览器 → 选文件 → 导入解析（看报告）→ 应用。
3. 右键一个方块：清空区域并铺设圆柱形音乐隧道（进度在动作栏）。
4. 空手右键圆心的"音乐控制器"：所有轨道同时起跑，你被传送到起点并随波前自动前行（按下 Shift 可脱离跟随）；再次右键停止；潜行右键拆除整个区域。

## 第四轮实测修复（v0.1.1）：旋律与音色

1. **废除"线上方"触发位（重要）**：反编译 + 实测双重确认——`SignalGetter.hasNeighborSignal` 对下方邻居传 `Direction.DOWN`，而红石线 `getSignal` 对 DOWN 一律返回 0，**红石线无法激活其上方的音符盒**。此前和弦第 3 音（往往是旋律最高音）被分到上方槽位全部静音，正是"听不出旋律"的主因。现在线容量 = 每槽左右枝路各 1，超复音自动拆新线。
2. **旋律优先**：同刻和弦按音高降序分配，最高音（旋律）优先占据枝路位置。
3. **前导空槽**：侧枝必须由"前一槽"红线馈电，槽 0 无馈电来源 → 全曲统一后移 1 槽（0.1s 不可感知），t=0 的音符不再被丢弃。
4. **钢琴族音色**：GM 0/1（钢琴）→ HARP（竖琴，柔和拨弦最接近钢琴本色，用户定稿）；GM 3（走音钢琴）→ PLING；未映射音色回退竖琴。
5. **轨道上限** 24 → 32；布局本就"由近到远"（右→左→头顶→正下→斜对角对…），线多了自动往更远的角度扩、半径自适应。

MIDI 事件翻译覆盖清单：Type 0/1/2、PPQ/SMPTE 时基、曲中变速（tempo map）、拍号、延音踏板 CC64、CC120/123 全部音关、Bank Select、Program Change（含中途换音色自动拆声部）、同键重叠截断、Note On 速度 0=Note Off、running status、SysEx 跳过。弯音/触后为音符盒无法表达的能力，解析报告会列出数量。

## 第八轮：均匀链（v0.1.2）——修复"周期性忽快忽慢"

用户实测：播放时周期性"慢一下、快一下、正常一会"循环。独立排查结论：**间隙压缩（8:1）是根因**——密集乐段波前 20 格/秒、静默间隙 2.5 格/秒，玩家载具跟随波前插值位置 → 速度随乐句结构周期性起伏（音符时刻本身始终精确）。

**修复**：废除间隙压缩，回归**每槽两格均匀链**（空槽也铺 红线+中继器 d=1）——波前与玩家全程恒速 20 格/秒，空间节奏 = 时间节奏。代价：隧道长度 ≈ 2×槽位数（3:33 曲目约 4400 格）、清空/铺设方块量小幅上升（多数清空为无操作跳过）。自检新增"相邻红线槽位 z 间距恒为 2"断言。

## 第九轮：逐音精确刻链（v0.2）——节奏完全复刻

用户两次提案合流的最终架构：**废除 0.1s 栅格 + 精密中继器 + 动态速度跟随**。

1. **精密中继器**（`precision_repeater`）：外观/模型直接引用原版中继器，但延迟以【游戏刻】为单位 1-200 任意设定（原版固定 2/4/6/8 刻）。通断调度复用 DiodeBlock 通用机制。
2. **逐音刻链**：无栅格。每个音符触发刻 = round(绝对秒×20)+1（≤25ms 误差、不累积）；链 = [启动源][精中继器 d=t₁][红线][精中继器 d=t₂−t₁][红线]…，**BPM 曲线与曲中变速直接烙进延迟序列**（变速验证：120→60BPM 场景 A@刻11/B@刻61 断言通过）。到达间隔超过 200 刻自动串联/插空到达点。
3. **动态速度跟随**（用户提案）：玩家载具逐刻追踪波前插值位置——速度的呼吸就是音乐的呼吸（长音漂、急奏飞）。链长正比于音符数而非时长（静默段一颗 200 刻中继器顶 20 格）。
4. 编排序列化 v3（ARM3，音符携带绝对触发刻）；自检逐音断言"馈电刻+枝路延迟 === 音符刻"。

## 第十轮：播放选项 UI + 观赏模式 + 摄像机模式（v0.3）

1. **播放选项 UI**：空手右键控制器不再直接播放，而是打开选项界面——经典模式（骑载具随波前）/ 观赏模式（载具落后波前 N 格、速度与波前一致，N 可调 0-30）/ 摄像机模式（离线渲染输出视频）。
2. **摄像机模式（单人；需系统安装 ffmpeg 并加入 PATH）**：
   - 冻结世界（isPauseScreen 空界面技巧使集成服务端停止 tick），客户端逐帧驱动虚拟时钟（每帧 20/fps 刻）；
   - 相机为客户端本地隐形盔甲架，固定向前视角、按"落后 N 格"沿波前路径滑动；材质包/光影正常生效（走正常渲染管线）；
   - 波前光效由客户端本地 setBlock 增量点亮（每帧只画增量）；
   - 每帧经 `Screenshot.takeScreenshot` 抓帧 → RGBA 字节流管道进 ffmpeg（libx264）→ 视频；
   - **音轨离线混音**：30 个采样由 ffmpeg 解码 PCM，按编排（触发刻/力度/音高重采样）混成完整演奏音轨 WAV（采样级精确，比游戏内 tick 播放更准），再与视频合成为 mp4；
   - 输出到 `游戏根目录/红石音乐视频/`；帧率 24/30/60 可选，分辨率 窗口/1080p/1440p/4K 可选（分辨率通过调整窗口实现）。
   - 已知边界：结束/退出时客户端本地点亮过的方块会由服务端区块重发校正；多服务端（专服）不支持摄像机模式。

## 第十一轮：实时录制模式（v0.3，真实声音 + 高分辨率）

用户需求："摄像机本身实时录制声音（含模组环境音），同时真实高分辨率高帧率画面"。

**关键发现**：26.1.2 的 `SoundEngine.updateSource(Camera)` —— **声音监听器跟随摄像机的位置与朝向**。因此摄像机在哪，录制到的声音方位就在哪，音画天然同源。

**实时录制模式（模式 4）**：世界真实运行（模组环境音/天气/生物真实发声），玩家骑载具以第一人称沿波前滑行（固定向前视角 = 摄像机），期间：
- **真实声音**：ffmpeg `dshow` 系统声音设备捕获（`Config.AUDIO_CAPTURE_DEVICE`，如"立体声混音"）——捕获系统混音输出 = 游戏全部声音（含模组环境音），无后期混音；
- **高分辨率**：通过 GLFW（反射 `Window.handle`）真实缩放窗口到目标分辨率（1080p/1440p/4K），渲染分辨率随之提升，录制结束恢复原窗口；
- **高帧率**：帧率可选 24/30/60/120；按**墙钟做帧复制/丢弃**——渲染快于目标帧率丢帧、慢于目标帧率复制补偿（上限 4×），保证视频时长与实际时长一致（音画同步）；
- 输出 `游戏根目录/红石音乐视频/乐曲名_live.mp4`。

**两种录制模式分工**：
| 模式 | 世界 | 画面 | 声音 |
|---|---|---|---|
| 摄像机（冻结离线渲染，模式 2） | 冻结 | 逐帧渲染，帧率/分辨率**保证**（4K120 无压力） | 离线混音（仅钢琴采样，采样级精确） |
| 实时录制（模式 4） | 真实运行 | 实时渲染上限 = 你的机器（窗口可放大到 4K） | **真实世界声音**（含全部模组环境音），dshow 捕获 |

> 实时录制需要：系统装有 ffmpeg；如需声音，需在 Config 里配置系统声音设备（`ffmpeg -list_devices true -f dshow -i dummy` 查询设备名；Windows 还需在声音设置中启用"立体声混音"）。

## 第十二轮：崩溃修复（v0.3.1）

**崩溃根因**：26.1.2 的 `RenderLevelStageEvent` 是**抽象类**，NeoForge 事件总线拒绝注册抽象类监听器（"Cannot register listeners for abstract class ... Register a listener to one of its subclasses instead!"）→ 模组加载期直接崩溃。修复：实时录制的抓帧钩子改挂具体子类 **`RenderLevelStageEvent.AfterLevel`**（每帧世界渲染结束、HUD 之前——录到的画面干净无 UI，正好合适）。

**同轮修正（冻结渲染模式）**：
1. 去掉了 `pauseGame()`——26.1.2 里 `pause` 状态由 `screen.isPauseScreen()` 自动推导（`Minecraft.runTick`），而 `pauseGame()` 反而会先弹一下暂停菜单；现在直接挂驱动界面即可。
2. **冻结机制全链路验证**：`IntegratedServer.tickServer` 每 tick 读 `Minecraft.isPaused()` → 服务端 tick 停止（红石完全静止）；客户端 `ticksToDo=0` → 逻辑静止；`renderFrame` 照常执行 → 逐帧渲染驱动成立。
3. 驱动界面 `extractBackground` 置空——默认会画模糊菜单背景，会录进视频。
4. 冻结模式下相机每帧 `setOldPosAndRot()`——客户端已冻结不再更新旧位置，强制同步让渲染精确落在设定点。

## 第十四轮：录制模式合并（v0.4）

用户反馈摄像机模式完全不可用、录制画面乱码。根因排查：

1. **画面乱码（决定性）**：`NativeImage.getPixels()` 返回**标准 ARGB（0xAARRGGBB）**，而转换 RGBA 字节序时 R/B 位取反了（`(byte)p` 取的是 B 当 R）——红蓝互换、画面彻底变色。且 `Screenshot.takeScreenshot` 已完成 Y 翻转（无需再翻）。
2. **落后波前配置不生效**：`glideCarriers` 与 `teleportToStart`/`mountCarrier` 三处都没减 `viewOffsetBlocks`（早前补丁未落盘）。
3. **默认视角错误**：`teleportToStart` 沿用了玩家当时的偏航角，未设为行进方向；且 startPlayback 里重复调用了两次传送。
4. 摄像机（冻结渲染）路线本身问题过多（中途抓帧、分辨率缩放、暂停交互），用户决定合并。

**合并后的"录制模式"（模式 2）**：
- 世界**实时运行**（模组环境音/天气正常），玩家骑载具以第一人称沿波前滑行，**朝向固定为行进方向**；
- **内录画面**：抓取主帧缓冲（AfterLevel，无 HUD），当前窗口分辨率，稳定优先（不再做窗口缩放）；墙钟帧复制/丢弃保证音画同步，帧率 24/30/60/120 可选；
- **内录游戏声音**：ffmpeg dshow 系统回环设备，**自动检测"立体声混音"**（无需手动配置；`Config.AUDIO_CAPTURE_DEVICE` 可手动覆盖），捕获即游戏实际输出（含模组环境音）；
- 播放结束（自然/手动停止）时服务端发 `RecordingStopPayload`，客户端立即优雅收尾（音频进程写 q 收尾防损坏）并与视频合成 mp4，输出到 `红石音乐视频/歌曲名.mp4`；
- 删除冻结渲染相关代码（CinematicRenderer/CinemaAudioMix/CinemaBeginPayload），UI 简化为三模式：经典/观赏/录制。

## 第十五轮：全乐器采样接管（v0.5）

用户要求：不仅钢琴，**全部 MIDI 乐器都由真实采样接管**（原版方块音色不一致且种类太少）。

**素材源（全部 CC0/CC-BY，可商用）**：
| 来源 | 内容 | 许可 |
|---|---|---|
| Salamander Grand Piano | 钢琴（既有） | CC-BY 3.0 |
| VSCO-2-CE（sgossner/VSCO-2-CE） | 独奏小提琴/中提琴/大提琴/低音提琴、弦乐群、小号/长号/圆号/大号、长笛/单簧管/双簧管/巴松/短笛 | CC0 |
| VCSL（sgossner/VCSL） | 竖琴、大键琴、管风琴、颤音琴/钟琴/马林巴/木琴/管钟、萨克斯、竖笛、TX81Z FM 合成器、完整鼓组 | CC0 |
| FreePats 西班牙古典吉他 | 吉他族 | CC0 |

**规模**：29 族 **433 采样**（每 2-3 半音一个根音），OGG 22050Hz 单声道共 **12MB**；模组 jar 11MB。

**架构（复用既有音高通道 + Mixin）**：
- `SampleTable`：族→根音表（构建脚本从 `_manifest.tsv` 生成）；`ModSounds` 按表注册全部 433 个声音（`族_根音`）
- 音高通道 v2 打包：**族(6b)|真实键(7b)|力度(7b)|折叠音(5b)**——Mixin 按族取采样，音高 = 2^((键−最近根音)/12)，**无界、全音域、零折叠**

## 第十六轮：存档卡死修复（v0.5.1）

用户反馈"起始方块确认后卡死、事件不刷新"。日志定位到**三个模组自身的问题**：

1. **致命：歌曲存档超 NBT 字符串上限**。`SongLibrary` 把整首歌 base64 存成单个字符串；NBT 单字符串硬上限 65535 字节（`NbtIo` 用 `writeUTF`），《花之舞》109KB→base64 145KB 远超 → **世界保存抛 `UTFDataFormatException`，存档写入持续失败**（每次 autosave 重试失败，表现为卡死/不刷新）。修复：base64 **分块**为 `List<String>`（每块 40000 字符），`Codec.either` 兼容读取旧单串格式。
2. **铺设同步区块加载卡顿**。62 万方块跨越 2879 格（≈180 区块），`setBlock` 到未加载区块触发**同步加载**——日志实测单次卡 14 秒/283 ticks。修复：铺设遇未加载区块**暂存 pending + `setChunkForced` 触发异步加载 + 本刻结束**（滑动窗口 48 块，超出释放最早的）；每刻预算 30ms→8ms；清空循环换序（轴向外层，先清近处一圈再向远推进，与加载节奏吻合）；完成/中止/拆除时释放全部 ticket。
3. **事件统计丢失**：NoteOn/NoteOff/变音色/控制器四个计数器在历次重写中丢失（日志显示全 0），已恢复；顺带修复了一处行拼接损伤（CONTROL_CHANGE 与 PITCH_BEND case 挤在一行）。

- **未来可选**：WorldEdit 式 section 直写（绕过 setBlock，最后统一补 邻块更新/光照/区块包）——速度再快一个数量级，但依赖 26.1 内部（调色容器/光照引擎/分区块包），风险高，暂不采用（记录于 开发规划.md M6）。

## 调试与排障（v0.1.1 起）

- **详尽调试开关**（两法任选，文件开关在下次打开 UI 时自动生效）：
  1. 启动参数 `-Darm.debug=true`；
  2. 在游戏根目录的 `midi` 文件夹里放一个名为 `.debug` 的空文件。
- 开启后所有 `[ARM-D]` 行以 INFO 级别写入 `logs/latest.log`：文件扫描数、解析统计、编排产物诊断（长度/魔数/SHA-1）、上传逐块跟踪、服务端收块、放置/启动/停止/清扫全程。
- 常开里程碑（无需调试开关）：解析完成、编排完成、上传开始/完成+校验、放置请求、解码成功、链编译通过、开始铺设、铺设进度（每 60 刻一条）、铺设完成、播放启动/停止、各类异常与停滞告警。
- **日志工具本身防崩溃**：`Log.render` 手动替换占位符，不经过 `java.util.Formatter`——字面量 `%`（如 "100%"）不会再触发 UnknownFormatConversionException 炸掉 BE tick（v0.1.1 崩溃事故的元凶，已根除）。
- **服务端完整性校验**：上传重组完成后校验总长 + SHA-1 与客户端声明一致，不一致立刻拒绝并输出双方摘要（此类问题不再表现为"编排损坏"）。
- 修复合入：v0.1.0 的"编排数据版本不匹配"是 UI 把 **MIDI 原始字节** 当编排产物上传所致（`applySelected` 应上传 `arrangement.toBytes()`），已修复并加完整性校验。
