### 0.3 音符盒与红石事实（反编译核实，这是本模组的物理基础）
- `NoteBlock`：属性 `INSTRUMENT / POWERED / NOTE(0–24)`；音高公式 `getPitchFromNote(n) = 2^((n-12)/12)`，即 note=12 为原调，**可弹范围 25 个半音（F#3–F#5，MIDI 54–78）**。
- **乐器从邻块推导**：`setInstrument()` 读音符盒**下方**方块的 `BlockState.instrument()`（或**上方**的"头顶乐器"如生物头颅）；26.1.2 中乐器是方块属性：`BlockBehaviour.Properties.instrument(NoteBlockInstrument)`。
- **乐器共 27 种**，其中可调音（BASE_BLOCK）20 种：HARP, BASEDRUM, SNARE, HAT, BASS, FLUTE, BELL, **GUITAR(新)**, CHIME, XYLOPHONE, IRON_XYLOPHONE, COW_BELL, DIDGERIDOO, BIT, BANJO, PLING, **TRUMPET/TRUMPET_EXPOSED/TRUMPET_OXIDIZED/TRUMPET_WEATHERED(新,铜号四态)**；另有 6 种生物头颅乐器 + CUSTOM_HEAD。
- **触发语义**：`neighborChanged` 检测到"开始有邻信号"（上升沿）时播放并置 POWERED；演奏本体通过 `level.blockEvent(pos, NOTE_BLOCK, 0, 0)` 广播（模组也可直接调用它强制触发）。
- **红石线供电方向**（`RedStoneWireBlock.getSignal`，已核实）：只对**正上方**方块（无条件）和**连线指向的**水平邻块供电；对下方、侧旁不指向的邻块一律不供电。⇒ **音符盒必须放在红石线正上方，或用 1 格枝线"指"进它**。
- 红石线在 26.1.2 默认求值器下**同刻瞬时传播**（updatePowerStrength 内联，无逐格延迟）⇒ 长红石线整条瞬间点亮，"行进感"只能由**中继器链**产生。
- `RepeaterBlock`：`DELAY(1–4)`，实际延迟 `DELAY×2` 游戏刻 = 0.1s×档位；仅向 `FACING` 正前方输出 15 信号；中继器可直接链中继器，也可 中继器→红石线→中继器。
- 红石块（`PoweredBlock`）向全部 6 邻方向输出 15 信号，是理想的"启动源/波前源"。

### 0.4 业界方案参考
- **mcpixelart.com/music**：网页导入 MIDI → 映射到音符盒音高/乐器/红石刻栅格 → 生成红石音乐电路蓝图（schematic/搭建指引）。核心是"MIDI→0.1s 红石刻栅格→物理红石布局"。
- **OpenNBS / Note Block Studio**（`import_midi` 脚本为参考实现）：GM 128 音色映射表 + GM 鼓组映射表（通道 10）、**2× 时间精度栅格**、超范围音符**按八度折叠进 33–57（F#3–F#5）**、按音色分"层"（=本模组的"轨道线"）。已知缺陷：八度折叠不跟踪方向导致音区错乱（issue #516）——本模组要规避。
- 另存在"直接播放 MIDI"类模组（如沉浸式奏乐），与本模组"物理红石音乐区域"定位不同，不冲突。

## 1. 模组定位与功能清单

**一句话**：把 MIDI 文件自动解析、自动编配（乐器匹配 + 轨道拆分），在世界中一键铺设一条"圆柱形包络"的物理红石音乐隧道；隧道起点圆心的控制器方块负责启动/停止/搬运玩家。

功能点（对齐需求原文）：
1. 加载模组后于**游戏根目录**自动创建 `midi/` 空文件夹，玩家放入 `.mid` 文件（后续可扩展其他格式：解析器做成接口）。
2. 注册**生成器**物品（含自制贴图）。
3. 手持生成器 **Shift+右键** 打开浏览 UI（风格照抄 entity_modifier：纯 Screen + 程序化绘制，无 gui 贴图）：浏览 `midi/` 下文件 → 一键导入解析（展示完整解析报告）→ 点击**应用**。
4. 应用后退出 UI，手持生成器**右键方块** → 清空区域 → 铺设轨道（自动拆分轨道、复合音符、乐器匹配、下方方块自动配置音色）→ 在起点圆截面圆心生成**控制器方块**并绑定。
5. **空手右键控制器** → 所有轨道的红石信号**同时**激活，玩家被传送到起点圆心并**随波前并行行进**（被红石音乐包裹）。再次右键停止。
6. 严格避免轨道重叠/冲突（几何隔离 + 同时刻复音拆分算法保证）。

## 3. 关键方案对比与选型（反思：有没有更优雅的方式？）

### 3.1 播放引擎 —— 【选 A：纯原版红石中继器链】为主，B 为可配置备选
> 起草时的第一反应是"模组 BlockEntity 每 2 刻移动一个红石块当波前"，但红石线瞬时求值 + 中继器链恰恰说明**纯原版方案可行且更优**（采纳讨论中"用中继器衔接控制速度"的思路，并已反编译验证其成立）。

| | A. 纯原版红石（中继器链） | B. 模组驱动波前（BE 移动红石块） |
|---|---|---|
| 触发原理 | 每轨道一条 `[中继器][红石线+音符盒于线上方]…` 链，DELAY=1 ⇒ **0.1s/2格，20格/s**；启动时控制器在每条线源头放红石块，全部同刻起跑 | BE 每 2 游戏刻在每条轨道"车道"移动一个红石块；`level.blockEvent` 兜底 |
| 运行时开销 | **零**（原版红石自行运转；模组仅搬运玩家） | 每刻 N 次方块读写 |
| 模组卸载后 | **建筑仍是可运转的原版红石音乐**（可导出 schematic 分享） | 停摆 |
| 停止 | 控制器移除源头红石块 + 一次性清扫 POWERED/POWER 显示位（防"余辉排空要几分钟"） | BE 停止即可 |
| 同时刻复音容量/线 | 1（线上方 1 格）；双侧枝线可到 2（宽 5） | 4（红石块六面全供能） |
| 计时精度 | 0.1s 栅格，由中继器延迟决定，**与服务器 tick 同源、绝对确定** | 0.1s 栅格，同 |
| 区块加载 | 两者都需要玩家随行加载（玩家被搬运 → 周围区块常载 → 波前永不脱载） | 同左 |
| 风险 | 链路被玩家破坏即断（可接受，原版红石同理） | 服务端逻辑复杂度集中 |

**结论**：默认 A。B 做成配置项 `playback-engine: vanilla_redstone | mod_driven`（布局引擎 95% 共用，仅音符盒位置与触发方式不同），既满足"真实红石音乐"的品味诉求，也保留高复音密度的退路。

**A 的三处坑（已在源码层面解决）**：
1. 红石线整条瞬时点亮 ⇒ **每节红石线必须且只能是 1 格**（两侧被中继器夹住），否则该节上的多个音符盒会同刻齐奏；
2. 停止后排空极慢（每个中继器 0.1s 逐个熄灭）⇒ 控制器停止时对全区域机械层做一次 `POWERED=false / POWER=0` 的状态清扫（确定性坐标遍历，一次 setBlock/格）；
3. 音符盒触发必须"线指入"或"线在上" ⇒ 采用**音符盒置于红石线正上方**（`getSignal(direction=UP)` 无条件供电，已核实）。

### 3.2 MIDI 解析 —— 自研 SMF 解析器（不用 javax.sound.midi）
- 自研 Standard MIDI File 解析（Type 0/1/2、变长数、running status、SysEx/Escape、全部 Meta 事件）代码量小（约 400 行）、无 `java.desktop` 模块依赖顾虑（专服/精简运行时安全）、对损坏文件可控降级、结果模型完全贴合后续分析需求。
- 解析产物 `MidiDocument`：division（PPQ 或 SMPTE）、tempo map（tick→微秒，支持曲中变速）、拍号/调号序列、轨道列表（名称、端口、通道集合、Program Change/Bank Select 序列、Note On/Off（含速度）、CC64 延音踏板、CC120/123 全部音关、弯音/触后计数）。
- 语义分析 `MidiAnalyzer`：以 tempo map 把全部事件换算成**绝对时间**；延音踏板正确延长音符截止；统计每轨音色、音符数、最低/最高音、最大复音数、鼓组轨（通道 10）；生成 UI 展示的解析报告与兼容性警告（如超范围音数量）。
- 未来扩展其他格式（.nbs / .abc / .json 歌谱）只需实现 `SongParser` 接口。

### 3.3 乐器映射
- 参照 OpenNBS 的 GM 映射思路 + 26.1.2 新乐器扩展，`InstrumentMapper` 内置 128 GM 音色 → 20 种可调音乐器的映射表（如：弦乐/人声垫→HARP，低音/贝斯→BASS，钢弦吉他→GUITAR，铜管→TRUMPET 族，钟琴类→XYLOPHONE/IRON_XYLOPHONE/BELL/CHIME，八音盒/盒铃→PLING/COW_BELL，电子→BIT，拨弦→BANJO/FLUTE/DIDGERIDOO…），未命中回退 HARP。
- **鼓组（通道 10）**：GM 鼓组键位映射 —— 底鼓(35/36)→BASEDRUM、军鼓(38/40)→SNARE、踩镲/开镲(42/44/46)→HAT、吊镲(49/57)→HAT 或 BELL、牛铃(56)→COW_BELL、其他打击→按音区就近映射；鼓组轨固定走独立线。
- **音色落地方式**：每个音符盒下方放置对应的**原版音色方块**（铁块=铁木琴、金块=钟、干草=班卓……），让 `NoteBlock.getStateForPlacement/updateShape` 按 26.1.2 规则自动推导 INSTRUMENT（完全原版行为，玩家后期可自行改造音色）。若某音色方块体积/获取成本过高，配置项允许"直接写 INSTRUMENT 方块属性 + 下方统一放轨道基座"的轻量模式（默认开原版方块模式）。
- 启动时可用 `BuiltInRegistries.BLOCK` 枚举 `defaultBlockState().instrument()` 反查"乐器→候选方块表"，避免硬编码被数据包改动破坏。

### 3.4 音高折叠
- MIDI 0–127 → 音符盒 0–24：按八度折叠（±12 迭代入界），**方向策略**：每条声部线以该线音域重心为锚，向最近八度折叠；折叠统计写入解析报告（UI 可见）。规避 NBS #516 的"盲目折叠破坏音区"。
- 鼓组音高保留（BASEDRUM/SNARE/HAT 也可调音），仅折叠不删除；同名同刻重复音去重。

### 3.5 时间栅格
- 全曲统一 0.1s（2 游戏刻）栅格：绝对时间 ÷ 0.1s 四舍五入；同槽音符按复音容量分配，超出容量自动拆线（见 3.6）。
- 快速乐句（<0.1s 间隔）被量化到同槽或邻槽，报告给出量化统计；不进行全局变速拉伸（保持速度恒定 20 格/s，乐曲多长隧道多长——"向前无限延伸"）。

### 3.6 轨道拆分与防重叠（需求重点）
分两层，逐层保证互不冲突：
1. **声部分组**：按 (端口, 通道, 当前 Program, 是否鼓组) 把全部音符聚成"声部组"；同一通道中途换音色会拆成多组。
2. **复音容量分配**：每组内按时间排序贪心分配到"线"上——线 L 在槽 t 已占用（A 模式容量 1，B 模式 4）则开新线；同组线连续编号。
3. **几何防重叠**：`CylinderLayout` 把线分配到圆柱截面圆周角度上，**线间距 ≥ 4 格**（含 5 格宽的中继器链走廊 + 视觉缓冲），半径自适应：`R = max(配置最小半径, ceil(线数×间距 / 2π))`；每条线独立计算包络，杜绝任何两线方块相交；中心轴留空给玩家通行；控制器占圆心。
4. 极端情况兜底：线数超过配置上限（如 24）时，按"音量权重=音符密度"合并次要声部（丢弃最稀疏组）并在报告中明示。

### 3.7 区域几何与铺设
- 玩家右键方块处 = **起点圆截面圆心**；轴向 = 玩家水平朝向（取 4 正方向）；截面为竖直圆，线 i 的角 θ_i 均布整圆（默认全圆；配置可切"上半圆"避免挖地下）。
- 每条线沿轴每隔 2 格一节：`[中继器(DELAY=1, FACING=轴向)][红石线]，音符盒在红石线正上方`；红石线/中继器下铺 `TrackRailBlock`（自定义基座），音符盒下方按 3.3 放音色方块（或轻量模式直接写属性）。
- **铺设前清空**：对圆柱包络（半径 R+2、轴向全长+前后缓冲）先清空（策略待确认，见问题清单）；随后按"每刻 ≤ N 个方块"分批放置（避免卡顿），期间控制器先就位并显示进度（动作栏文字）。
- 区域参数（songId、圆心、朝向、半径、线数、槽数、布局模式）全部存入控制器 BE ⇒ **放置/清拆/重建完全确定性**，重启后仍可一键拆除（Sneak+右键控制器或生成器 Sneak+右键控制器）。
- 长度上限：槽数 = 乐曲时长×10，配置 `max-song-length-blocks`（默认 4096，约 6.8 分钟），超出时拒绝并在 UI 提示（待确认，见问题清单）。

### 3.8 控制器方块与播放时序
- 外观：自制贴图（扬声器/八分音符母题），BaseEntityBlock，`useWithoutItem` 交互。
- **空手右键**（未播放）：① 每条线源头旁放置红石块（同刻全部激活 ⇒ 满足"所有音轨同时激活"）；② 把右键玩家传送到起点圆心（面向正前）；③ 播放期间每 2 刻把跟随玩家沿轴**瞬移 1 格**（与波前同步，玩家脚下区块持续加载保证波前永不进入未加载区块；被传送玩家可 Sneak 脱离跟随，脱离后音乐继续、由该玩家视距继续加载，若波前追上未加载区块则自动暂停等待——专服多人安全）。再右键可加入跟随。
- **再次右键**（播放中）：移除源头红石块 + 一次性清扫显示位（3.1-A-2）+ 结束跟随。
- **Sneak+右键**：整区域清拆（确定性坐标遍历置 air），释放 BE 绑定。
- 自然结束：最后一个音符槽 + 2s 缓冲后自动执行"停止"动作。
- 播放期间控制器区块自我强载（`TicketType` 强制加载自身区块，结束时释放），防止玩家前进而圆心控制器 BE 停 tick 导致跟随中断。

### 3.9 UI 设计（照抄 entity_modifier 风格）
- 纯 `Screen` + `graphics.fill/outline/text` 程序化绘制，零 gui 贴图；控件移植 `GuiLayoutHelper` 自适应布局（MIN_GUI_WIDTH=320）。
- 布局：左侧文件列表（`midi/*.mid`，扫描于打开时；刷新按钮）+ 右侧详情面板（未解析：文件名/大小；解析后：时长、PPQ、曲速表、拍号/调号、每轨通道/音色/音符数/音域/复音峰值/鼓组标记、八度折叠与量化统计、警告列表）+ 底部按钮行：`刷新 | 导入解析 | 试听(可选) | 应用 | 取消`。
- "导入解析"在后台线程执行（文件可达数 MB），完成后填充报告；"应用"= 转换 `SongArrangement` 二进制 → 分块上传 → 服务端确认 → 关闭 UI 并提示"右键方块放置"。
- "试听"（可选，第一版可砍）：客户端用 `level.playLocalSound(SoundEvents.NOTE_BLOCK_HARP…, pitch)` 按栅格本地预览 8 小节。

### 3.10 网络协议
| Payload | 方向 | 内容 |
|---|---|---|
| `UploadSongBeginPayload` | C→S | 文件名、总字节数、分块数、sha1 |
| `UploadSongChunkPayload` | C→S | 序号 + ≤28KB 字节块（规避服务端包上限，逐块重组校验） |
| `PlaceMusicPayload` | C→S | 暂存歌曲 id、放置锚点由右键位置推导（也可并入物品 useOn 的服务端逻辑，UI 只做"选定"） |
| `ControlMusicPayload` | C→S | 控制器坐标 + 动作(开始/停止/拆除/跟随开关) |
| `ActionFeedbackPayload` | S→C | 成功/失败/进度（动作栏提示） |
所有 payload 走 `registrar("1")`，服务端全部校验（距离、权限、暂存存在性）。

### 3.11 持久化
- `SongLibrarySavedData`（世界级）：songId → SongArrangement（Codec/二进制），控制器 BE 只存 songId + 几何参数 + 状态；世界重载后控制器的启停/清拆照常工作。
- `PendingSongStore`：应用→放置的暂存用内存 Map（玩家 UUID → 歌曲），登出清理；同曲重复放置直接从库里取。
- 源 `.mid` 不复制、解析缓存可选写入 `midi/.cache/<sha1>.arr.bin`（二次导入秒级）。

## 4. 边界情况与兼容性
- **Type-0**（全轨单轨）：按通道+音色自动分组，等价 Type-1 处理；**Type-2**：按"曲段"顺序拼接。
- **SMPTE 时基**（负 division）：按帧率×分辨率换算绝对时间。
- **曲中变速/拍号**：tempo map 全程生效（绝对时间化后栅格量化天然正确）。
- **弯音/触后/表情控制器**（CC1/11 等）：音符盒无法表达，记录进解析报告；CC64 延音正确延长音符；CC120/123 截断悬挂音。
- **极端复音**（管弦乐 MIDI 一刻 20+ 音）：拆线+半径自适应+上限合并（3.6-4）。
- **重复放置**：新区域独立并存（各自 BE），互不干扰；同点重复放置=先清拆旧的再建。
- **多人**：所有动作服务端裁决；跟随玩家列表支持多人同时跟随。
- **卸载模组后**：A 引擎的建筑照常人工启动（红石块手动放上源头即可）。

## 5. 性能预算
- 放置：每刻批量 ≤1000 setBlock，5 分钟曲（约 3000 槽 × 12 线 × ~4 块/槽·线 ≈ 15–40 万方块）预计 30–120 秒完成，全程动作栏进度。
- 播放：A 引擎零模组开销；红石机械本身负载与 mcpixelart 级人工建筑相当。
- 清拆：同样分批；确定性遍历无需存储方块清单。
- 解析：10 万音符级 MIDI 后台线程 < 1s。

## 8. 决策记录与遗留问题

### 8.1 已拍板（2026-10-06 确认）
1. **清空强度**：区域内（含地形）**全部清空**；默认仅创造模式可执行清空，生存模式需配置 `region.clear-mode` 开启（防误拆）。
